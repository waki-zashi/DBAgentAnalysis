# DBagentAnalysis — стенд оценки LLM-генерации правил качества данных

Стенд проверяет, начиная с какого размера языковая модель способна заменить аналитика в задаче
формирования правил проверки качества данных (data quality rules) для реляционной БД.

Идея эксперимента: берём **чистую** БД, **контролируемо и воспроизводимо** вносим в неё дефекты
с построчным журналом, даём модели схему и описание предметной области и просим сформировать правила
проверки в виде SQL. Журнал внедрения служит эталоном (ground truth): по нему автоматически считаются
recall и precision найденных моделью нарушений.

Этот README описывает слой данных: чистую БД, процедуру загрязнения и самопроверку стенда.

---

## Быстрый старт

```bash
pip install -r requirements.txt
python generate_clean.py 42      # чистая БД -> data/clean.duckdb, data/clean/*.csv
python inject_faults.py 2026     # грязная БД -> data/dirty.duckdb, data/dirty/*.csv, журнал
python verify.py                 # самопроверка стенда, должно закончиться "STAND OK"
```

Скрипты запускаются из корня проекта. Аргумент — seed. Одинаковые seed и версии пакетов дают
побайтно одинаковые CSV (проверяется по sha256 в манифестах).

## Структура проекта

| Файл | Назначение |
|---|---|
| `schema.sql` | DDL пяти таблиц. Без PK/FK/NOT NULL/CHECK — см. «Почему нет ограничений» |
| `generate_clean.py` | Генерация чистой БД и проверка 17 инвариантов |
| `faults.json` | Каталог дефектов: ID, уровень, измерение качества, таблица, количество, описание |
| `inject_faults.py` | Внедрение дефектов в копию чистой БД, запись журнала |
| `oracle_rules.sql` | Эталонные правила аналитика: по одному SQL на дефект |
| `verify.py` | Самопроверка: эталонные правила на чистой БД дают 0 строк, на грязной — ровно журнал |
| `common.py` | Общие пути, чтение/запись БД, экспорт CSV, манифесты |
| `CHANGES.md` | **Генерируется.** Сводка всех внесённых изменений: таблицы, количества, примеры |
| `data/clean.duckdb` | Чистая (эталонная) БД |
| `data/clean/*.csv` | Снимок чистой БД в CSV, отсортирован по первичному ключу |
| `data/clean_manifest.json` | seed, версии пакетов, число строк и sha256 каждой таблицы чистой БД |
| `data/dirty.duckdb` | Загрязнённая БД — именно её получает модель |
| `data/dirty/*.csv` | Снимок загрязнённой БД в CSV |
| `data/dirty_manifest.json` | То же для грязной БД плюс ссылка на манифест чистой |
| `data/journal.json` | **Эталон.** Построчный журнал: какой дефект, какие строки-нарушители, какие изменения |
| `data/changes.csv` | Плоская таблица всех атомарных изменений (одна строка — одно изменение) |

## Чистая БД

### Предметная область

Интернет-магазин: клиенты, каталог товаров, заказы, позиции заказов, платежи.
Данные синтетические (Faker `ru_RU` + numpy), поэтому:

- все инварианты выполняются **по построению**, ноль нарушений до загрязнения доказывается проверкой;
- схема и данные уникальны, модель не могла видеть их при обучении (нет контаминации, в отличие от
  Northwind/Sakila/Chinook);
- реальные датасеты (например, Olist) не подходят: в них уже есть неизвестные нам дефекты, а значит
  нет эталона.

### Почему нет ограничений

В схеме нет PK, FK, NOT NULL, UNIQUE и CHECK — только типы. Это моделирует staging-слой хранилища,
куда данные приходят из множества источников без проверок: правила качества нужны именно потому,
что СУБД их не гарантирует. Техническая причина: с ограничениями DuckDB не дал бы внедрить висячие
ссылки, дубли и NULL в обязательных полях.

Логические ограничения модель получает из **словаря данных** ниже — как аналитик получает их из
документации.

### Схема и словарь данных

**customers** — клиенты (2000 строк)

| Столбец | Тип | Обяз. | Описание |
|---|---|---|---|
| customer_id | INTEGER | да | Идентификатор клиента, уникален |
| full_name | VARCHAR | да | ФИО. Совпадение ФИО у разных клиентов допустимо |
| email | VARCHAR | да | Email, уникален без учёта регистра, формат `local@domain.tld` |
| phone | VARCHAR | **нет** | Телефон, клиент может не указать |
| birth_date | DATE | да | Дата рождения; клиенту не больше 120 лет и он родился до регистрации |
| city | VARCHAR | да | Город доставки |
| registered_at | TIMESTAMP | да | Момент регистрации |

**products** — товары (150 строк)

| Столбец | Тип | Обяз. | Описание |
|---|---|---|---|
| product_id | INTEGER | да | Идентификатор товара, уникален |
| name | VARCHAR | да | Название |
| category | VARCHAR | да | Категория: electronics, books, clothing, home, toys, sports, beauty, food |
| price | DECIMAL(10,2) | да | Текущая цена, руб., > 0 |
| stock_qty | INTEGER | да | Остаток на складе, ≥ 0 |

**orders** — заказы (6000 строк)

| Столбец | Тип | Обяз. | Описание |
|---|---|---|---|
| order_id | INTEGER | да | Идентификатор заказа, уникален |
| customer_id | INTEGER | да | Ссылка на `customers.customer_id` |
| status | VARCHAR | да | Одно из: `new`, `paid`, `shipped`, `delivered`, `cancelled` |
| ordered_at | TIMESTAMP | да | Момент оформления, не раньше регистрации клиента |
| shipped_at | TIMESTAMP | по статусу | Момент отгрузки |
| delivered_at | TIMESTAMP | по статусу | Момент доставки |
| total_amount | DECIMAL(12,2) | да | Сумма заказа = Σ quantity · unit_price по позициям |

**order_items** — позиции заказов (≈13,3 тыс. строк)

| Столбец | Тип | Обяз. | Описание |
|---|---|---|---|
| order_item_id | INTEGER | да | Идентификатор позиции, уникален |
| order_id | INTEGER | да | Ссылка на `orders.order_id` |
| product_id | INTEGER | да | Ссылка на `products.product_id` |
| quantity | INTEGER | да | Количество, > 0 |
| unit_price | DECIMAL(10,2) | да | Цена за единицу на момент заказа, > 0 |

**payments** — платежи (≈4,9 тыс. строк)

| Столбец | Тип | Обяз. | Описание |
|---|---|---|---|
| payment_id | INTEGER | да | Идентификатор платежа, уникален |
| order_id | INTEGER | да | Ссылка на `orders.order_id` |
| amount | DECIMAL(12,2) | да | Сумма платежа = `orders.total_amount` |
| paid_at | TIMESTAMP | да | Момент оплаты: после оформления и до отгрузки |
| method | VARCHAR | да | `card`, `sbp`, `wallet`, `cash_on_delivery` |

### Бизнес-правила (инварианты чистой БД)

Жизненный цикл заказа:

| status | shipped_at | delivered_at | Платёж |
|---|---|---|---|
| new | NULL | NULL | нет |
| paid | NULL | NULL | ровно один |
| shipped | есть | NULL | ровно один |
| delivered | есть | есть | ровно один |
| cancelled | NULL | NULL | нет |

Остальные инварианты:

- `ordered_at ≤ shipped_at ≤ delivered_at`;
- `ordered_at ≥ customers.registered_at`;
- `ordered_at ≤ paid_at ≤ shipped_at`;
- у каждого заказа есть хотя бы одна позиция;
- `orders.total_amount = Σ quantity · unit_price`, `payments.amount = orders.total_amount`
  (суммы считаются в целых копейках, погрешности округления нет);
- все внешние ключи ссылаются на существующие строки;
- email уникален без учёта регистра.

`generate_clean.py` проверяет 17 инвариантов (словарь `INVARIANTS`) и падает, если хоть один нарушен.

### Характеристики данных (seed = 42)

| Показатель | Значение |
|---|---|
| Регистрации клиентов | 2022-01 … 2024-06 |
| Заказы | 2022-01 … 2025-06 |
| Статусы | delivered 3583, shipped 685, cancelled 651, paid 585, new 496 |
| Позиций на заказ | 1–5 (35 / 30 / 20 / 10 / 5 %) |
| Цены товаров | логнормальные, 102 … 26 918 руб., медиана ≈ 1 577 |
| Отгрузка после заказа | 6–96 ч; доставка после отгрузки 1–10 сут. |

Точные числа строк и хэши — в `data/clean_manifest.json`.

### Ловушки (законные особенности чистых данных)

Нужны для честной precision: правило, которое на них срабатывает, — ложная тревога.

- `phone` пуст примерно у 26 % клиентов — поле необязательное;
- `shipped_at`/`delivered_at` пусты у `new`, `paid`, `cancelled` (и `delivered_at` у `shipped`) —
  так и должно быть;
- 15 пар однофамильцев: одинаковое ФИО, разные email — это не дубли;
- цены и суммы заказов имеют тяжёлый правый хвост — наивное правило выбросов по IQR даст много
  ложных срабатываний;
- `unit_price` — цена на момент заказа; в общем случае она может расходиться с текущей
  `products.price` (в дефекте F04 это происходит).

### Фиксация чистой версии

Чистая версия зафиксирована тремя способами:

1. `data/clean.duckdb` — сама БД;
2. `data/clean/*.csv` — текстовый снимок, который удобно смотреть глазами и сравнивать в git;
3. `data/clean_manifest.json` — seed, версии Python и пакетов, число строк и sha256 каждого CSV.

`verify.py` первым делом сверяет CSV-снимок с манифестом. Если чистая версия случайно изменилась,
стенд сообщит об этом.

## Загрязнение

### Каталог дефектов

19 дефектов, 3 уровня сложности; полный список с описаниями — `faults.json`, фактические числа —
`CHANGES.md`.

| Уровень | Что требуется от правила | Дефекты |
|---|---|---|
| **L1** — один столбец | Полнота, формат, допустимые значения, диапазон | F01–F07 |
| **L2** — несколько столбцов / агрегаты | Дубли, порядок дат, статус ↔ даты, выбросы | F08–F12 |
| **L3** — несколько таблиц | Висячие ссылки, суммы между таблицами, платежи, регистрация ↔ заказ, пустые заказы | F13–F19 |

При seed = 2026 внедрено 1058 строк-нарушителей.

### Принципы загрязнения

1. **Одна строка — один дефект.** Для каждой таблицы ведётся пул ещё не затронутых строк, дефекты
   берут строки из него без возвращения. Заказ, к позиции которого применён дефект, тоже выбывает
   из пула. Без этого, например, порча `total_amount` автоматически породила бы расхождение
   с платежом, и одну строку пришлось бы приписать двум дефектам.
2. **Согласованное распространение.** Дефекты на уровне позиции (F05 — неположительное
   количество, F12 — выброс цены) пересчитывают `total_amount` заказа и сумму платежа: ошибка
   «пришла из источника», а производные поля посчитаны от неё честно. F15 (неверная сумма заказа)
   меняет и платёж — деньги списали по неверной сумме. Поэтому каждый дефект виден ровно одному
   эталонному правилу.
3. **Строки-нарушители, а не изменённые строки.** Для удалений и вставок нарушитель — не всегда
   изменённая строка: при F17 удаляется платёж, а нарушителем является заказ; при F08/F09
   вставляется копия клиента, а нарушители — обе строки пары.

### Формат журнала `data/journal.json`

```json
{
  "seed": 2026, "clean_seed": 42, "faults": [...],
  "entries": [
    {
      "fault": "F17", "level": "L3", "dimension": "consistency",
      "targets": [{"table": "orders", "pk": 1234}],
      "note": null,
      "changes": [
        {"op": "delete", "table": "payments", "pk": 987, "column": null,
         "old": {"payment_id": 987, "order_id": 1234, "...": "..."}, "new": null}
      ]
    }
  ]
}
```

- `targets` — эталон для оценки: какие строки должно найти правило;
- `changes` — что физически изменено (`update` / `insert` / `delete`, старое и новое значение).

Тот же список изменений в плоском виде — `data/changes.csv`, человекочитаемая сводка — `CHANGES.md`.

## Самопроверка стенда

`oracle_rules.sql` содержит эталонные правила — то, что написал бы аналитик. Каждое правило
возвращает первичные ключи строк-нарушителей своей таблицы. `verify.py` проверяет:

- CSV-снимок чистой БД совпадает с манифестом;
- каждое эталонное правило на чистой БД возвращает 0 строк;
- на грязной БД каждое правило возвращает **ровно** множество `targets` своего дефекта из журнала
  (`missed = 0`, `extra = 0`);
- для каждого дефекта в журнале есть эталонное правило.

Только при `STAND OK` можно переходить к прогону моделей.

## Контракт для правил модели

Чтобы правила модели автоматически сопоставлялись с журналом, каждое правило — один `SELECT`,
первая колонка результата — первичный ключ строки-нарушителя. Метрики:

- precision правила r: `|R_r ∩ T| / |R_r|`, где T — все строки-нарушители той же таблицы;
- покрытие дефекта f: `max_r |R_r ∩ T_f| / |T_f|`;
- execution rate, доля обращений к несуществующим таблицам/столбцам — по ошибкам выполнения.

Модель работает с `data/dirty.duckdb` только через соединение `read_only=True`: изменить данные
или схему технически невозможно.

## Воспроизводимость

- seed чистой БД и seed загрязнения задаются аргументами и записываются в манифесты и журнал;
- версии Python и пакетов записываются в манифесты; побайтное совпадение гарантируется при тех же
  версиях (в первую очередь Faker и numpy);
- `.gitattributes` отключает преобразование концов строк для `data/`, иначе git на Windows изменил
  бы CSV и хэши перестали бы совпадать.
