# DBagentAnalysis — стенд оценки LLM-генерации правил качества данных

Стенд проверяет, начиная с какого размера языковая модель способна заменить аналитика в задаче
формирования правил проверки качества данных (data quality rules) для реляционной БД.

Идея эксперимента: берём базу данных, у которой есть **чистая** и **грязная** версии с известными
дефектами, даём модели схему и описание предметной области и просим сформировать правила проверки
в виде SQL. Построчный журнал нарушений служит эталоном (ground truth): по нему автоматически
считаются precision и coverage найденных моделью нарушений.

Этот README описывает слой данных: источник БД, как построен журнал нарушений и самопроверка
стенда.

---

## Быстрый старт

```bash
pip install -r requirements.txt
python build_university_bench.py   # скачивает дампы датасета, парсит их, пишет diff_report.txt
python finalize_bench.py           # собирает schema.sql, clean.duckdb, dirty.duckdb, journal.json
```

Скрипты запускаются из корня проекта. Скачанные дампы кэшируются в `data/uni_raw/` — повторный
запуск `build_university_bench.py` их не перекачивает.

## Структура проекта

| Файл | Назначение |
|---|---|
| `build_university_bench.py` | Скачивает чистый и грязный Postgres-дамп, парсит `CREATE TABLE`/`INSERT INTO`, пишет построчный diff-отчёт |
| `finalize_bench.py` | Строит `schema.sql`, `data/clean.duckdb`, `data/dirty.duckdb` и `data/journal.json` из разобранных дампов |
| `schema.sql` | DDL 30 таблиц. Без PK/FK/NOT NULL; дата/время — VARCHAR (см. «Почему нет ограничений») |
| `common.py` | Общие пути и список таблиц (`TABLES`) |
| `prompt.py` | Системный промпт для агента: DDL + словарь данных |
| `data/uni_raw/` | Кэш скачанных дампов, сырая схема, diff-отчёт — промежуточные файлы, не часть эталона |
| `data/clean.duckdb` | Чистая БД датасета |
| `data/dirty.duckdb` | Грязная БД датасета — именно её получает модель |
| `data/journal.json` | **Эталон.** Построчный журнал: какой дефект, какие строки-нарушители |

## Источник данных

[University sample database](https://databasesample.com/datasets/university-sample-database) —
синтетический датасет об университете (CC0, общественное достояние), размер **1K**: 30 таблиц,
6962 строки на пике (`enrollments` = 1000). Автор датасета публикует одновременно чистую версию и
версию с внедрёнными дефектами (missing values, typos, outliers, дубли/почти-дубли, разные форматы
дат, висячие внешние ключи) — но без построчного журнала, только агрегированные счётчики по
столбцам.

Выбор именно этого датасета (а не собственной e-commerce генерации, как в первой версии стенда):

- настоящая многотабличная структура с реальными FK-цепочками (`enrollments → students/sections`,
  `invoices → semesters/students` и т.д.) — больше материала для L3-проверок, чем в плоской схеме
  на 5 таблицах;
- дефекты внедрены независимо от нас — это не самоинъекция одного и того же автора, который потом
  сам же и проверяет;
- CC0, можно свободно ссылаться на источник.

### Предметная область

Люди, адреса, учебные программы, курсы и их секции (конкретные запуски курса в семестре),
преподаватели и студенты, запись на секции и оценки, экзамены и задания, счета и оплаты,
стипендии, библиотека, клубы. Полный словарь данных и бизнес-правила — в `prompt.py`
(`DATA_DICTIONARY`), который и получает модель в системном промпте.

### Почему нет ограничений

В `schema.sql` нет PK, FK, NOT NULL, UNIQUE и CHECK — только типы. Это тот же staging-слой,
что и в первой версии стенда: правила качества нужны именно потому, что СУБД их не гарантирует.
Техническая причина у дат и времён отдельная: в грязной версии часть значений — не просто другая
дата, а дата в другом текстовом формате (`20231114`, `11/07/2024`, `Jan 6, 2023`) или вовсе
непарсящийся мусор. Типизированная колонка `DATE`/`TIMESTAMP` такие строки не примет вообще, поэтому
все столбцы дат/времени в обеих БД — `VARCHAR`, а их синтаксическая валидность — то, что должна
проверять модель (например, через `try_cast(col AS DATE) IS NULL`).

## Как построен журнал нарушений

В отличие от первой версии стенда (там дефекты вносили сами и сразу писали журнал), здесь дефекты
внесены автором датасета — у нас нет готового построчного эталона, его нужно восстановить.

`build_university_bench.py` скачивает оба Postgres-дампа (1K, см. выше) и парсит их напрямую —
без промежуточной БД: регекс на `CREATE TABLE` даёт схему, ручной токенизатор на
`INSERT INTO ... VALUES (...)` (с учётом кавычек, экранирования `''` и вложенных скобок) — данные.

`finalize_bench.py` сравнивает чистую и грязную версии **построчно по `id`**:

1. Для строк, присутствующих в обеих версиях, — сравнение значения в каждом столбце. Отличие
   классифицируется по шаблону:
   - значение стало `NULL` → `missing_value` (L1, completeness);
   - строка стала `ВСЕМИ ЗАГЛАВНЫМИ` → `case_anomaly` (L1, validity);
   - число сменило знак → `sign_flip_outlier` (L1, accuracy);
   - число выросло в 10 раз → `scale_outlier` (L1, accuracy);
   - дата/время в столбце с суффиксом `_date`/`_at`/`_time` перестала парситься как ISO и похожа на
     другой формат (`\d{8}`, `DD/MM/YYYY`, `Mon D, YYYY`) → `mixed_date_format` (L1, validity);
   - столбец `..._id` стал указывать на несуществующую строку в таблице, на которую ссылается по
     названию (`student_id → students.id` и т.п.) → `fk_orphan` (L3, referential_integrity);
   - всё остальное (опечатки в свободном тексте: `tSreet`, `Wesetrn`, `nO Principles` и т.п.) →
     `value_changed_other` (L1, validity) — это и есть категория «typo» из описания датасета;
     SQL-правило в общем случае не может надёжно поймать опечатку в произвольном тексте без
     внешнего словаря, поэтому ожидаемое покрытие этой категории у всех моделей низкое — это
     содержательный результат, а не брак стенда.
2. Для строк, присутствующих только в грязной версии (новый `id`), — `duplicate_row` (L2,
   uniqueness). Для каждой такой строки стенд ищет в чистой версии строку с точно совпадающими
   значениями всех столбцов кроме `id`; если находит — это точный дубль, и обе строки идут в
   `targets`; если нет — почти-дубль, и нарушителем считается только новая строка.

Каждая пара (категория, таблица) получает свой `fault id` (например `MISSING_VALUE__addresses`,
`FK_ORPHAN__enrollments`) — так можно смотреть покрытие не только по уровню L1/L2/L3, но и по
конкретной таблице и типу дефекта.

### Проверка корректности журнала

Так как дефекты внесены не нами, нужна независимая проверка, что diff и классификация верны:

- автор датасета указывает для 1K-версии агрегированные числа дефектов; у стенда `missing_value`
  даёт **596** — ровно то же число, что заявлено на странице датасета;
- все 46 найденных `fk_orphan` подтверждены явной проверкой «значения действительно нет среди `id`
  родительской таблицы в чистой версии» — ложных срабатываний 0;
- `data/uni_raw/diff_report.txt` — человекочитаемый дифф по каждой таблице и столбцу с примерами
  `старое → новое`, можно сверить глазами.

Итоговое распределение (1008 атомарных изменений на 1К-версии):

| Категория | Кол-во | Уровень | Измерение |
|---|---:|---|---|
| missing_value | 596 | L1 | completeness |
| duplicate_row | 112 | L2 | uniqueness |
| value_changed_other (опечатки) | 108 | L1 | validity |
| case_anomaly | 92 | L1 | validity |
| fk_orphan | 46 | L3 | referential_integrity |
| scale_outlier | 25 | L1 | accuracy |
| mixed_date_format | 18 | L1 | validity |
| sign_flip_outlier | 11 | L1 | accuracy |

### Формат журнала `data/journal.json`

```json
{
  "source": "databasesample.com university-sample-database v2 flagship 1k",
  "faults": [
    {"id": "FK_ORPHAN__enrollments", "level": "L3", "dimension": "referential_integrity",
     "table": "enrollments", "description": "..."}
  ],
  "entries": [
    {"fault": "FK_ORPHAN__enrollments", "level": "L3", "dimension": "referential_integrity",
     "targets": [{"table": "enrollments", "pk": 389}],
     "note": "student_id: 25 -> 439", "changes": []}
  ]
}
```

`targets` — эталон для оценки: какие строки должно найти правило. Формат совместим с первой
версией стенда, поэтому `evaluate.py`/`agent.py`/`run_matrix.py`/`aggregate.py` не изменились.

## Контракт для правил модели

Каждое правило модели — один `SELECT`, первая колонка результата — первичный ключ (`id`) строки
в указанной таблице. Метрики:

- precision правила r: `|R_r ∩ T^(t)| / |R_r|`, где T^(t) — все строки-нарушители той же таблицы;
- покрытие дефекта f: `max_r |R_r ∩ T_f| / |T_f|` (максимум по правилам, а не объединение — чтобы
  нельзя было набрать покрытие сотней случайных правил);
- execution rate, schema hallucination rate — по ошибкам выполнения SQL.

Модель работает с `data/dirty.duckdb` только через соединение `read_only=True`.

## Воспроизводимость

- `data/uni_raw/clean.sql.gz` и `data/uni_raw/dirty.sql.gz` — кэш исходных дампов, после первого
  запуска сеть больше не нужна;
- `finalize_bench.py` детерминирован: один и тот же вход даёт один и тот же `journal.json` и обе БД;
- `.gitattributes` отключает преобразование концов строк для `data/`.

## Эксперимент: ReAct-агент

### Архитектура

DuckDB — встраиваемая СУБД, поэтому БД не поднимается в контейнере и не слушает сеть. По сети
ходят только запросы к API моделей. Цикл одного эпизода:

```
оркестратор (agent.py) ──HTTP──> API модели (GigaChat / Groq через litellm)
        ^                              │ ответ: tool_call run_sql(sql) или submit_rules(rules)
        │                              v
        └── tools.run_sql: валидация -> duckdb.connect(dirty.duckdb, read_only=True) -> результат
```

- **run_sql** — разведка: один `SELECT`/`WITH`, запрещённые ключевые слова отсекаются до
  исполнения, таймаут 5 с через `con.interrupt()`, модели возвращается не более 20 строк;
- **submit_rules** — финальный ответ: список `{table, dimension, description, sql}`;
- бюджет — 15 обращений к модели; за шаг до конца модели напоминают сдать правила; эпизод без
  `submit_rules` получает статус `incomplete` и нулевое покрытие;
- системный промпт (`prompt.py`) — задача, DDL всех 30 таблиц и полный словарь данных с бизнес-
  правилами и законными особенностями данных.

### Модели (`models.py`)

| Семейство | Модели | Провайдер | Роль |
|---|---|---|---|
| GigaChat 2 | Lite, Pro, Max | GigaChat API | лестница размеров (размеры не раскрыты, только ранг) |
| GPT-OSS | 20B, 120B | Groq | бинарная пара |

Qwen3 (OpenRouter) и Llama (Groq `llama-3.1-8b-instant`/`llama-3.3-70b-versatile`) исключены из
матрицы: первая — платная ($0.08–0.28 за 1M токенов на момент эксперимента), вторая — снята с
бесплатного/developer-тарифа Groq 16.08.2026. Groq (gpt-oss) и GigaChat используются по
бесплатной квоте.

### Метрики (`evaluate.py`)

Правило r для таблицы t возвращает множество ключей R_r; T_f — нарушители дефекта f из журнала,
T^(t) — все нарушители таблицы t.

- execution rate — доля правил, выполнившихся без ошибки;
- schema hallucination rate — доля правил с несуществующими таблицами/столбцами;
- precision(r) = |R_r ∩ T^(t)| / |R_r|, усредняется по правилам;
- coverage(f) = max_r |R_r ∩ T_f| / |T_f|; усредняется по дефектам уровня L1/L2/L3.

### Запуск

`.env` в корне проекта (в git не попадает):

```
GIGACHAT_AUTH_KEY=...     # Authorization key (base64 client_id:client_secret)
GROQ_API_KEY_1=...
```

Точные имена переменных значения не имеют — `settings.py` принимает несколько распространённых
алиасов на каждый ключ.

```bash
pip install -r requirements.txt
python check_providers.py                              # какие ключи найдены и какие модели отвечают с tool calling
python run_matrix.py --models gpt-oss-20b --repeats 1   # пробный эпизод
python run_matrix.py --models gigachat-lite gigachat-pro gigachat-max gpt-oss-20b gpt-oss-120b --repeats 5
python aggregate.py                                     # таблица + графики
```

`run_matrix.py` пропускает уже посчитанные прогоны (`--force` — пересчитать), поэтому его можно
прерывать и перезапускать.
